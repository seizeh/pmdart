# ADR-0008: 상태관리 프레임워크 없이 `ChangeNotifier` 홀더

- 상태: 채택 (2026-07) — 재평가 예정
- 관련: `docs/architecture-state.md`(패턴 상세), `lib/state/`, 이슈 #155·#156

## 맥락

화면 59개, `setState` 를 쓰는 파일 62개. 1,000줄 넘는 화면이 8개고 그중
`business_register_screen.dart` 는 2,065줄이다. 상태가 위젯 트리에 붙어 있어
**테스트에서 떼어낼 수 없는 것**이 진짜 문제였다(커버리지 12% 의 구조적 원인 —
[ADR-0007](0007-coverage-ratchet.md)).

여기서 선택지는 둘이었다.

1. Riverpod/Bloc 같은 프레임워크를 도입하고 전면 마이그레이션
2. 프레임워크 없이 상태를 위젯 밖으로 꺼내는 패턴을 정하고 화면 단위로 전환

## 결정

**2번.** `lib/state/<화면>_state.dart` 에 `ChangeNotifier` 상태 홀더를 두고, 화면은
`ListenableBuilder` 로 구독해 **그리기만** 한다.

- 홀더는 위젯 트리·`BuildContext` 를 참조하지 않는다 — **테스트 가능성의 핵심**
- 협력자는 생성자 주입 가능하게(`{Repo? repo}`), 기본값은 기존 싱글턴
- 내비게이션·다이얼로그 등 `BuildContext` 가 필요한 일만 화면에 남는다

근거:

- 코드베이스의 기존 관용구와 일치한다 — `SessionManager`·`ThemeController` 가 이미
  `ChangeNotifier`, 화면 간 이벤트는 `AppEvents`(`ValueNotifier`)
- 의존성 0, **화면 단위 점진 전환** 이 가능하다(전면 마이그레이션 강제 없음)
- God Widget 구조 위에 프레임워크를 얹으면 **레이어만 늘고 경계는 그대로**다.
  분해가 진행돼 상태 경계가 드러난 뒤 재평가하는 게 순서다

## 결과

- 현재 홀더 6개(알림함·게시글 상세·채팅방·내 정보·프로필 편집·사용자 프로필).
  화면 59개 중 6개라는 뜻이고, **나머지는 아직 규칙이 없다**
- 홀더 테스트는 `test/state/` 에 — FakeSupabase(http 목킹)로 리포지토리까지 실코드 관통
- **적용 규칙:** 새 화면은 이 구조로. 기존 화면은 손댈 일이 생길 때 그 화면부터 전환

## 정직한 평가 — 다시 만든다면

이건 "프레임워크가 필요 없다" 는 주장이 **아니다.** 초기 속도를 위해 `setState` 로 시작한
결과 테스트 불가능한 구조가 됐고, 지금은 그 부채를 갚는 중이다. 다시 시작한다면
**처음부터 상태를 위젯 밖에 두고, DI 를 넣고, 리포지토리를 인터페이스로 잡는다.**

프레임워크 도입(#156)을 지금 하지 않는 이유는 "필요 없어서" 가 아니라
**분해가 끝나기 전에 도입하면 잘못된 경계를 굳히기 때문**이다. 순서는 #155 → #156 이다.
