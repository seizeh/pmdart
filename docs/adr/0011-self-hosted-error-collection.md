# ADR-0011: 오류 수집을 외부 SaaS 가 아니라 우리 DB 로

- 상태: 채택 (2026-07). **Sentry 도입 결정을 되돌린 것이다.**
- 관련: `lib/services/observability.dart`, `lib/services/error_reporter.dart`,
  `pmdb/supabase/migrations/20260731080000_client_error_collection.sql`,
  `docs/error-policy.md`, 이슈 #157, PR #213(닫음)·#219·#223

## 맥락

전역 오류 훅이 없어 **위젯 빌드 예외와 처리되지 않은 비동기 예외가 어디에도 안 남았다**
(#157, [`docs/error-policy.md`](../error-policy.md)). 릴리스에서는 콘솔조차 없다.

표준 해법은 Sentry 다. 실제로 `sentry_flutter` 를 붙였고 DSN 을 CI 시크릿에 넣고
`deploy-web.yml` 까지 고쳤다. **그리고 되돌렸다.**

되돌린 이유는 기술적 실패가 아니다. 붙이는 과정에서 두 가지가 드러났다.

### 1. 개인정보처리방침 — 이게 결정적이었다

Supabase 는 **이미 개인정보 처리위탁 수탁자**로 방침에 고지돼 있다(`pmlegal`).
오류를 우리 Supabase 로 보내는 것은 **수탁자 목록이 안 바뀐다.**

Sentry 는 다르다. 수탁자가 하나 늘고, 국외이전 고지가 필요하다. 오류 리포트에는
사용자 식별자·스택·컨텍스트가 실리므로 "개인정보가 안 간다" 고 말할 수도 없다.
베타 시작 전에 방침을 개정하고 재동의 흐름을 검토해야 한다는 뜻이다.

**관측성을 위해 법무 작업을 하나 늘리는 거래**였고, 그 값이 얻는 것보다 컸다.

### 2. CSP — 부수적이지만 실측으로 확인됐다

`sentry_flutter` 는 웹에서 `browser.sentry-cdn.com` 의 JS SDK 를 `<script>` 로 끼워 넣는다.
`web/_headers` 의 `script-src` 를 열어야 한다. 브라우저는 이걸 503 으로 보고했지만
`curl` 은 200 이었다 — 네트워크가 아니라 CSP 가 막고 있었다는 뜻이다.
`connect-src` 에는 우리 Supabase 가 이미 있어서 자체 수집은 헤더를 안 건드린다.

## 결정

**`app.client_errors` 테이블 + `public.record_client_error` RPC 로 직접 받는다.**

```
ErrorReporter.report(...)
  → SupabaseErrorSink
  → public.record_client_error   (SECURITY DEFINER, anon 실행 가능)
  → app.client_errors            (RLS 정책 0개, 30일 보존)
  → 관리자 앱 → 클라이언트 오류
```

RPC 를 **`anon` 에게도 연다.** 웹은 비로그인 방문자가 주 진입로라 그들의 오류를 못 받으면
목적의 절반이 사라진다. 공개 쓰기 엔드포인트가 되므로 넷을 전제로 깔았다.

| 전제 | 구현 |
|---|---|
| 레이트리밋 | 로그인 30/분, 익명 `ip_hash` 별 30/분(+ 전역 300/분) |
| 서버측 절단 | `message` 500자 · `stack` 8,000자 · `extra` 4,000자 |
| 예외 삼킴 | 서버·클라이언트 양쪽. 오류 보고가 또 오류를 만들면 안 된다 |
| 등급 제한 | `reported` 만 (무시·사용자알림은 링 버퍼에만) |
| 파기 | `cleanup_retention()` 이 30일 지난 행 삭제 |

## 검토한 대안

| 대안 | 기각 사유 |
|---|---|
| Sentry (실제로 도입 후 철회) | 수탁자 추가 → 방침 개정·국외이전 고지. 베타 전 치를 비용이 얻는 것보다 컸다 |
| 자체 호스팅 GlitchTip | 서버 한 대가 더 생긴다. 1인 운영에서 관측성 인프라의 가용성을 또 챙길 수 없다 |
| Supabase Logs 만 사용 | 서버측 로그다. **클라이언트에서 난 예외는 애초에 안 올라온다** |
| 아무것도 안 함 | #157 의 출발점. 릴리스에서 오류가 통째로 안 보인다 |

## 결과

**잃은 것을 먼저 적는다.**

- **그룹핑·중복제거 없음.** 같은 오류 1,000건이 1,000행이 된다
- **릴리스 간 비교 없음.** "이 배포부터 늘었다" 를 자동으로 못 본다(`app_release` 로 손으로 본다)
- **소스맵·심볼리케이션 없음.** 릴리스 스택은 난독화된 채로 남는다
- **알림 없음.** 급증해도 아무도 안 깨운다 — 관리자 화면을 열어야 안다

대신 **발생 지점별 집계**(`admin_client_error_summary`)로 "어디가 자주 터지나" 를 본다.
베타 규모(5~10명, launch-checklist §7)에서는 그룹핑의 값이 작다고 봤다.

**되돌리는 비용은 낮게 유지했다.** 앱은 `ErrorReporter.sink` 하나만 보고,
`SupabaseErrorSink` 는 그 인터페이스의 구현 하나다. 사용자가 늘어 그룹핑이 필요해지면
**sink 만 갈아끼우면 되고 앱 코드는 한 줄도 안 바뀐다.** 그때는 방침 개정 비용을
치를 이유도 같이 생겨 있을 것이다.

### 실제로 밟은 함정

**증상 1 — 웹에서 오류가 하나도 안 잡혔다.**
원인은 부팅 순서였다. `main()` 은 `SessionManager.load()`(67행)를
`Supabase.initialize()`(99행)·`Observability.bootstrap()`(128행)보다 **먼저** 부른다.
그 사이에 난 `session.restoreUser` 오류는 sink 가 붙기 전이라 서버로 갈 수 없었다.
→ `ErrorReporter` 에 링 버퍼를 남겨 두고 `flushPending()` 으로 부팅 후 흘려보낸다(PR #222).

**증상 2 — 개발 중 위젯 어서션 36건이 운영 테이블에 쌓였다.**
디버그 빌드가 곧장 서버로 보내고 있었다. 관리자 홈을 몇 번 여는 것만으로 그렇게 됐고,
그 상태면 실사용자 오류가 개발 노이즈에 묻힌다.
→ 디버그 기본값을 콘솔로 내리고 `REPORT_ERRORS_IN_DEBUG=true` 로만 켠다(PR #223).
갈래가 셋이라 눈으로는 또 틀려서 `Observability.resolveSink` 로 떼어내 테스트로 고정했다.

**증상 3 — 익명 레이트리밋이 자기 텔레메트리를 가릴 수 있었다.**
익명 전체가 단일 버킷 300/분이었다. 방문자 한 명의 브라우저에서 오류 루프가 돌면
그 사람이 300/분을 혼자 태우고 **그동안 다른 모든 방문자의 오류가 조용히 버려진다** —
하필 제일 알고 싶은 순간에 눈이 먼다.
→ `post_views` 가 이미 쓰던 `ip_hash` 로 키를 쪼개 개별 30/분으로 바꿨다.
전역 300/분은 그대로 두되 **개별 상한이 먼저 걸리게** 순서를 잡았다.

**증상 4 — 그 고침의 주석에 검증하지 않은 신뢰 주장을 적었다.**
"IP 는 서버가 직접 뽑는다(**클라이언트가 못 속인다**)" 라고 썼는데, 코드는
`x-forwarded-for` 의 맨 왼쪽 항목을 쓰고 있었다. XFF 는 프록시가 **뒤에** 덧붙이는
헤더라 맨 왼쪽은 클라이언트가 주장한 값이다. 운영에 직접 쏴서 확인했다:

| 요청 | 서버가 본 `x-forwarded-for` |
|---|---|
| 위조 없음 | `115.91.115.38` (실제 IP) |
| `X-Forwarded-For: 9.9.9.9` | `9.9.9.9,115.91.115.38` ← **맨 왼쪽이 공격자 값** |

XFF 를 매 요청 바꾸면 30/분 버킷이 무한히 생겨 1단이 무력화된다.
같은 방식으로 다른 헤더도 쟀다:

| 헤더 | 위조 시도 결과 |
|---|---|
| `x-forwarded-for` | 통과 — 맨 왼쪽이 공격자 값 |
| `x-real-ip` · `sb-forwarded-for` | 무시됨(엣지가 걷어내고 실제 IP 유지) |
| `cf-connecting-ip` | **엣지가 요청 자체를 거부**(Cloudflare 1000) — DB 까지 오지 못한다 |

→ `cf-connecting-ip` 로 바꿨다. 헤더가 없으면 XFF 로 **폴백하지 않는다** —
폴백이 곧 우회로가 되기 때문이다. 공용 버킷으로 떨어뜨리고 2단 전역이 받는다.
고친 뒤 같은 검증을 다시 돌려 40회(XFF 매번 다름) → 30건으로 확인했다.

이 프로젝트는 [ADR-0003](0003-definer-view-write-paths.md) 에서 "공개 anon 키만으로
관리자 승격이 됐다" 를, `isMocked` 에서 "자기신고는 신뢰 근거가 아니다" 를 이미
겪었다. **그러고도 같은 종류의 단정이 다시 들어갔다.** 교훈은 "헤더를 조심하라" 가
아니라 **"못 속인다" 는 문장을 쓸 때는 속여 보고 나서 쓴다** 는 것이다.
피해가 작았던 건 2단 전역 상한이 남아 있었기 때문이지 판단이 옳아서가 아니다.

## 왜 이 결정을 문서로 남기나

이건 기술 비교표로 안 나오는 결정이다. 기능·가격·성능만 보면 Sentry 가 이긴다.
**제품이 서 있는 제약(개인정보 방침의 수탁자 목록)을 읽어야 뒤집힌다.**

되돌린 결정이라 더 남길 값이 있다. 도입까지 갔다가 철회한 경로 자체가 근거다 —
`sentry_flutter` 의존성 추가, DSN 시크릿 설정, CSP 헤더 수정, 그리고 철회.
이 ADR 이 없으면 다음 사람(혹은 6개월 뒤의 나)이 같은 길을 다시 간다.
